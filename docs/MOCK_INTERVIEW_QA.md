## 一、项目概览

### Q1：先用几句话介绍一下你的项目。

**回答：**

我的项目叫 `SuperMew`，它本质上是一个基于 `RAG + Agent` 的智能知识库问答系统。用户可以上传 `PDF / Word / Excel` 文档，系统会自动完成文档解析、分块、向量化、存储和检索；之后用户通过聊天提问，系统会从知识库中检索相关内容，再让大模型结合检索结果生成最终回答。

这个项目不只是“调用一个大模型接口”，而是做成了一个完整的 AI 应用。它包含：

- 前端聊天界面
- 用户注册登录和权限控制
- 会话历史记录
- 文档上传和知识库管理
- RAG 检索链路
- 流式输出
- 检索过程可视化 trace

如果用一句话总结，我会说：

> 它是一个面向知识问答场景的、具备工程化能力和可解释性的 AI 助手系统。

---

### Q2：这个项目主要解决了什么问题？

**回答：**

它主要解决的是“大模型不知道企业私有知识”这个问题。

大模型虽然通用能力很强，但它有两个明显限制：

1. 它不知道你的本地文档、公司制度、项目资料。
2. 它容易幻觉，也就是一本正经地编答案。

所以我的项目的核心目标，就是把用户自己的文档变成一个可检索的知识库，再让大模型基于检索到的真实内容来回答。这样做有几个好处：

- 回答更贴近用户自己的资料
- 能显著减少幻觉
- 可以展示引用来源和检索过程
- 支持随着文档更新而更新知识

也就是说，这个项目不是在追求“大模型什么都知道”，而是在追求“大模型能基于你的资料可靠地回答”。

---

### Q3：这个项目和普通聊天机器人最大的区别是什么？

**回答：**

普通聊天机器人更多是“通用对话”，它主要依赖模型本身的训练知识。而我的项目是“知识增强型聊天系统”，最大的差别在于它有一整套外部知识增强机制。

核心区别有四点：

- 它支持用户上传自己的文档，构建私有知识库。
- 它不是直接回答，而是先检索、再判断、再生成。
- 它支持混合检索、重排、查询改写等较完整的 RAG 链路。
- 它把检索过程和检索结果以 trace 的方式展示出来，增强可解释性。

所以它更像一个“有大脑的大模型 + 有记忆的知识库 + 有执行逻辑的应用系统”，而不是一个单纯的对话页面。

---

### Q4：你觉得这个项目最能体现技术亮点的地方是什么？

**回答：**

我觉得有五个最值得讲的亮点。

第一，`Hybrid Retrieval`。我没有只做稠密向量检索，还结合了 `BM25` 稀疏检索，在 Milvus 中做混合召回，这样既能理解语义，又不容易漏掉关键词、编号、专业术语。

第二，`三层分块 + Auto-merging`。我把文档切成 L1、L2、L3 三层，叶子块负责精确检索，父块负责上下文聚合。这样能兼顾召回精度和回答上下文完整性。

第三，`查询改写策略`。我不是只检索原始问题，而是在检索效果不好时，引入 `step-back`、`HyDE`、`complex` 三种扩展策略，提高复杂问题的命中率。

第四，`实时 trace`。系统会把“正在检索、正在评分、正在重写查询、正在重排”等步骤实时推送到前端，这对用户体验和系统可解释性帮助很大。

第五，`工程化设计`。它有用户体系、权限、Redis 缓存、PostgreSQL 持久化、Milvus 向量存储、流式 SSE 输出，这说明它不是实验脚本，而是完整应用。

## 二、架构设计

### Q5：你的项目整体架构是怎样的？

**回答：**

整体上可以分成四层。

第一层是前端展示层。  
前端基于 `Vue 3 CDN` 实现，负责聊天界面、登录注册、文档上传、历史会话展示，以及流式渲染回答和 trace。

第二层是 API 和业务层。  
后端使用 `FastAPI`，负责提供聊天接口、文档管理接口、认证接口、流式输出接口。

第三层是 AI 编排层。  
这里由 `LangChain Agent` 和 `LangGraph` 组成。Agent 决定什么时候调用工具；RAG 工具内部再通过 LangGraph 执行检索、评分、改写和扩展检索的流程。

第四层是数据存储层。  
这里用了三个核心存储：

- `PostgreSQL`：存用户、会话、消息、父块文档
- `Redis`：做热点缓存
- `Milvus`：存向量和检索元数据

所以整个系统是比较典型的“前端 + API + AI 工作流 + 多存储协作”架构。

---

### Q6：为什么后端选择 FastAPI？

**回答：**

主要是因为这个项目很适合 `FastAPI`。

第一，它天然适合 API 项目。这个项目核心就是聊天 API、登录 API、文档管理 API。

第二，它对异步支持很好。我的流式输出、SSE、异步事件队列，都更适合用 FastAPI。

第三，它和 `Pydantic` 集成很好。项目里有很多请求响应模型，比如登录请求、聊天响应、RAG trace 模型，FastAPI + Pydantic 在这方面开发体验很好。

第四，它自带接口文档。开发和调试时可以直接用 `/docs` 查看和测试。

简单说，如果项目重点是“高效搭建 API + 支持流式交互 + 类型明确”，FastAPI 是很合适的。

---

### Q7：为什么数据要拆成 PostgreSQL、Redis、Milvus 三种存储？

**回答：**

因为这三类数据的特点完全不同，用同一个存储会很别扭。

`PostgreSQL` 适合结构化数据。  
比如用户信息、会话、消息记录、权限、父块文档，这些都有明确字段、关系和持久化需求，所以放在关系型数据库里最合适。

`Redis` 适合高频读写和热点缓存。  
比如会话消息、会话列表、父块内容，这些用户会频繁访问，如果每次都查 PostgreSQL，开销会更大，所以我用 Redis 做缓存。

`Milvus` 适合向量检索。  
文档片段的稠密向量、稀疏向量，以及向量相似搜索，都属于向量数据库最擅长的场景。

所以这不是“技术堆砌”，而是按数据特性做的合理分工。

---

### Q8：前端为什么没有用完整的工程化框架，而是 Vue CDN？

**回答：**

这是一个偏“应用原型 + AI 能力验证”的项目，所以我当时优先考虑的是开发效率和集成成本，而不是前端脚手架的完整度。

用 `Vue 3 CDN` 有几个实际好处：

- 不需要额外构建流程
- 部署简单
- 对单页聊天应用已经够用
- 可以更快把重点放在 AI 链路上

当然，如果后续要继续扩展成正式产品，我会考虑迁移到 `Vite + Vue` 或者 `React + Next.js`，这样前端的模块化、状态管理和工程能力会更强。

所以这里不是“不会用框架”，而是“根据项目阶段做了取舍”。

## 三、RAG 核心流程

### Q9：用户提问后，系统内部完整链路是怎样的？

**回答：**

完整链路可以分成八步。

1. 用户在前端输入问题。
2. 前端调用 `POST /chat/stream`。
3. FastAPI 进入流式对话处理函数。
4. Agent 判断是否需要调用知识库工具。
5. 如果调用 `search_knowledge_base`，就进入 LangGraph RAG 流程。
6. RAG 流程执行检索、评分、查询改写、二次检索。
7. 检索结果回到 Agent，Agent 再生成最终回答。
8. 回答和 trace 一起通过 SSE 流式推送给前端，并最终落库。

这里最关键的一点是：  
“检索”和“生成”不是混在一起的，而是先由工具链做知识增强，再由模型做自然语言生成。

这让整个系统的结构更清晰，也更方便追踪和优化。

---

### Q10：为什么你要用 Agent，而不是直接调用一个 RAG 函数？

**回答：**

因为我想让系统具备“工具选择能力”，而不是只会固定走知识库。

项目里除了知识库检索工具，还有天气工具。未来也可能扩展更多工具，比如网络搜索、数据库查询、任务规划等。  
如果我把逻辑写死成“所有问题都必须走 RAG”，那系统的扩展性会很差。

Agent 的价值在于：

- 能根据用户问题判断是否调用工具
- 能选择不同工具
- 能把工具结果整合进最终回答

所以 Agent 更像一个“调度层”，而 RAG 是其中一个重要工具。

---

### Q11：你的 RAG 流程为什么要用 LangGraph？

**回答：**

因为我的 RAG 已经不是单一步骤了，而是一个有分支判断的状态流。

如果只是“检索一次然后回答”，直接写函数也可以。  
但我的流程里有：

- 初次检索
- 相关性评分
- 是否需要改写查询的判断
- 多种改写策略选择
- 扩展检索
- 最终 trace 汇总

这时候用 `LangGraph` 很合适，因为它擅长表示这种“状态机式”的工作流。

我把问题、上下文、检索结果、扩展查询、trace 等都放进 `RAGState` 里，不同节点对这个状态做更新。这种写法比把所有逻辑塞进一个大函数里更清晰，也更方便以后继续加节点。

---

### Q12：你这个 RAG 图里有哪些核心节点？

**回答：**

核心有四个节点。

`retrieve_initial`  
用用户原始问题做第一次检索，并把检索结果写进上下文和 trace。

`grade_documents`  
让模型判断当前检索结果和问题是否足够相关。它本质上是一个“要不要继续优化检索”的路由节点。

`rewrite_question`  
如果结果不够好，就先重写查询。这里不是简单同义改写，而是会根据问题类型选择不同策略。

`retrieve_expanded`  
基于扩展查询或者 HyDE 生成的假设文档，再做一次检索，并把结果去重、排序、写入 trace。

也就是说，这张图做的事情不是回答问题，而是把“找到更合适的上下文”这件事做扎实。

---

### Q13：为什么你要在检索后加一个文档相关性评分节点？

**回答：**

因为“检索返回了结果”不等于“结果真的好用”。

很多时候，向量检索能召回一些看起来相关、但其实不足以回答问题的片段。  
如果直接拿这些片段去生成，回答质量会不稳定，甚至可能让模型误答。

所以我加了 `grade_documents` 节点，让模型先做一次二元判断：

- `yes`：这批结果已经足够相关，可以进入回答阶段
- `no`：这批结果不够好，需要继续做查询改写

这个设计的价值在于，它让系统从“检索一次就硬答”升级成“先判断，再决定是否补救”，会明显更稳。

---

### Q14：这个评分节点会不会很耗时？为什么还要加？

**回答：**

会增加一点延迟，但我认为是值得的。

因为对 RAG 系统来说，最怕的不是“慢一点”，而是“检索错了还强行回答”。  
一旦上下文错了，后面的生成往往也会错，而且这种错误用户不容易发现。

加一个评分节点，相当于给系统加了一个“质量门”。它的意义不只是提分，更是降低错误回答的概率。

另外我这里的评分不是让模型长篇分析，而是用结构化输出给出 `yes/no`，这比开放式回答更稳定，也更容易解析。

---

## 四、项目创新点一：混合检索

### Q15：什么是混合检索？你为什么要做它？

**回答：**

混合检索，就是把“稠密向量检索”和“稀疏关键词检索”结合起来。

稠密向量检索的优点是懂语义。  
比如“怎么清除缓存”和“缓存失效策略是什么”虽然字面不完全一样，但语义相关，向量检索更容易找到。

稀疏检索的优点是抓关键词。  
比如某个专业名词、接口名、错误码、文件名、版本号，这类词在 BM25 里往往更有优势。

如果只用向量检索，可能会漏掉关键词很强但语义不明显的内容。  
如果只用 BM25，又可能理解不了自然语言表达。

所以我做混合检索，是为了同时利用两者的优点，让召回更全面、更稳。

---

### Q16：你这个项目里的混合检索具体是怎么实现的？

**回答：**

实现上主要有三步。

第一步，给每个文档块生成两种表示：

- 稠密向量：用 HuggingFace 的 embedding 模型生成
- 稀疏向量：我自己维护 BM25 统计后生成

第二步，把这两种向量都写入 Milvus。  
也就是说，同一个 chunk 在 Milvus 里同时有：

- `dense_embedding`
- `sparse_embedding`

第三步，检索时同时发起两路检索请求，再用 `RRF` 做结果融合。

这样最终得到的不是单一路径结果，而是两路检索综合之后的排序结果。

---

### Q17：为什么 Milvus 里同时存稠密和稀疏向量？

**回答：**

因为我要在同一个检索系统里同时支持语义搜索和关键词搜索。

如果把稠密和稀疏拆到两个完全不同的系统里，后续融合、过滤、统一分页都会更麻烦。  
而 Milvus 本身支持多向量字段和混合检索，所以我就直接把两种表示都放进去。

这样做的好处是：

- 检索入口统一
- 过滤条件统一
- 结果融合更自然
- 架构更简洁

从工程上说，这比“一个向量库 + 一个搜索引擎 + 再自己做大整合”更轻量。

---

### Q18：为什么你选择 RRF 做融合，而不是简单加权？

**回答：**

`RRF` 的优点是鲁棒、简单、少调参。

如果用简单加权，比如 `0.7 * dense_score + 0.3 * sparse_score`，会遇到一个问题：  
不同检索方式的分数空间不一样，直接线性相加不一定合理，还要做归一化和大量调参。

而 RRF 更关注“排名”而不是“原始分数”，意思是：

- 只要某个结果在某一路里排得很靠前，它就能得到较高融合分
- 不需要过度依赖原始分值尺度

对于我这个项目来说，RRF 的好处就是：

- 实现简单
- 效果稳定
- 不容易因为分值尺度不同导致融合异常

所以它很适合做工程上的第一版融合方案。

---

### Q19：你为什么没有直接接 Elasticsearch，而是自己做 BM25 并写入 Milvus？

**回答：**

这是一个很典型的面试追问。

我这样设计主要有三个考虑。

第一，统一性。  
我希望检索主要围绕 Milvus 这一套完成，而不是再额外维护一个搜索引擎集群。

第二，项目规模。  
当前项目是中小规模知识库场景，用 Milvus 的稀疏向量能力已经够支撑实验和应用级场景。

第三，工程复杂度。  
如果引入 ES，虽然也很强，但系统复杂度会上升，需要额外维护索引同步、一致性、部署和监控。

所以我的选择是：  
先在当前体系里把混合检索做好。如果未来文档量更大、搜索需求更复杂，再考虑引入 ES 或 OpenSearch。

---

## 五、项目创新点二：BM25 状态持久化

### Q20：BM25 这一块你觉得最有创新感的实现是什么？

**回答：**

我觉得最值得讲的是：  
我没有把 BM25 当成一次性算分工具，而是把它做成了“可持久化、可增量更新的状态系统”。

我在本地维护了这些统计量：

- 词表 `vocab`
- 文档频次 `doc_freq`
- 文档总数 `total_docs`
- 总 token 长度 `sum_token_len`

这些信息会持久化到 `bm25_state.json`。  
这样系统重启以后，BM25 状态不会丢；新增文档时可以增量更新；删除文档时也可以把对应统计扣掉。

这件事听起来不大，但其实很关键，因为它保证了稀疏向量的“长期一致性”。

---

### Q21：为什么 BM25 状态不能每次启动都重新计算？

**回答：**

理论上可以，但工程上很不划算。

如果每次启动都重新计算，就意味着：

- 需要重新扫描所有文档
- 启动成本很高
- 状态容易和向量库里的数据不一致

更关键的是，我这里把稀疏表示写进了 Milvus。  
如果词表每次重建都变，维度映射就可能变掉，之前写进去的数据和当前状态就会对不上。

所以我才把 BM25 状态持久化下来，让它成为一个稳定的长期索引状态，而不是临时变量。

---

### Q22：删除文档时为什么还要同步更新 BM25 统计？

**回答：**

因为如果只删 Milvus 里的向量，不删 BM25 统计，系统的检索状态就会失真。

比如某个关键词原来出现在很多 chunk 里，后来文档删掉了。如果 `doc_freq` 还保留旧值，那后面的 IDF 计算就不准确了。

这会导致两个问题：

- 稀疏分数不再反映真实语料
- 新数据和旧统计会不一致

所以我在删除文档前，会先根据文件名把所有相关 chunk 文本找出来，然后调用 `increment_remove_documents` 去同步扣减 BM25 状态。

这个细节能说明我不是只关注“能跑”，而是关注“长期运行后是否一致”。

---

## 六、项目创新点三：三层分块与 Auto-merging

### Q23：为什么你要做三级分块，而不是普通固定长度分块？

**回答：**

因为普通固定长度分块虽然简单，但在 RAG 场景里有一个常见问题：

- 分太小，检索准确但上下文碎
- 分太大，上下文完整但检索不够精细

所以我做了三层结构：

- L1：大块，语义范围广
- L2：中块，作为过渡层
- L3：小块，作为检索叶子节点

检索时优先检索 L3，因为它最精细。  
但如果多个 L3 都命中了同一个父区域，我就可以向上合并成 L2 甚至 L1，拿到更完整的上下文。

这个设计本质上是在解决“精确召回”和“完整上下文”之间的矛盾。

---

### Q24：为什么只有叶子块写入 Milvus，父块不写？

**回答：**

这是一个典型的“精度和成本平衡”设计。

叶子块更短、更聚焦，适合做向量检索。  
如果把父块也写进 Milvus，会出现两个问题：

- 向量冗余更多，占用更多存储
- 检索结果可能混杂粗粒度和细粒度块，排序更复杂

所以我的方案是：

- 叶子块负责被召回
- 父块负责在必要时补上下文

这样既保留了精细检索能力，又节省了向量存储和索引成本。

---

### Q25：Auto-merging 的核心思想是什么？

**回答：**

它的核心思想是：

> 如果多个叶子块同时命中了同一个父块区域，那就说明用户真正需要的可能是这个更完整的上层上下文。

举个简单例子。  
如果某个问题的答案分布在连续三个小片段里，而这三个小片段都属于同一个父块，那么与其把三个零散片段分别给模型，不如直接把对应父块给模型。

这样有两个好处：

- 上下文更完整，模型更容易组织答案
- 结果展示更自然，不会显得特别碎

所以 Auto-merging 实际上是在提升“召回结果的可用性”，而不只是提升“召回命中率”。

---

### Q26：Auto-merging 的触发条件是什么？

**回答：**

触发条件很直接：  
把当前检索结果按 `parent_chunk_id` 分组，如果某个父块下命中的子块数达到阈值，就触发合并。

项目里这个阈值是可配置的，默认是 2。也就是说，只要一个父块下至少命中两个子块，就认为它足够有价值，可以提升到父块级别。

之后系统会：

- 根据父块 ID 去 `ParentChunkStore` 中取父块内容
- 用父块替代多个子块
- 再做去重和排序

这套逻辑是分两段做的：

- L3 -> L2
- L2 -> L1

所以它不是一次性暴力合并，而是逐层向上收敛。

---

### Q27：为什么父块要单独放 PostgreSQL，而不是继续放 Milvus？

**回答：**

因为父块的价值主要不是“检索”，而是“取回和拼装上下文”。

既然父块不参与主要向量检索，那就没必要也给它建向量索引。  
把它放 PostgreSQL 反而更合适，因为：

- 它本质上是结构化文档片段数据
- 可以按 ID 快速查
- 可以配合 Redis 缓存
- 成本比向量库存储更低

所以这个设计体现的是“按职责放数据”。

---

## 七、项目创新点四：查询改写

### Q28：为什么你要做 query rewrite？

**回答：**

因为用户问题和知识库文本的表达方式经常不一致。

比如用户会问：

- “这个系统为什么卡住？”
- “这个接口应该怎么走？”
- “缓存机制具体是怎么做的？”

但文档里不一定这样写，它可能写成：

- “系统阻塞场景”
- “调用链路设计”
- “Redis 缓存策略”

如果只检索原问题，可能能召回一些东西，但不一定是最好结果。  
所以 query rewrite 的作用就是把问题变成更适合检索的形式。

它可以显著提升复杂问题、模糊问题和抽象问题的召回质量。

---

### Q29：你的 query rewrite 有哪些策略？

**回答：**

有三种：

`step_back`  
把具体问题抽象成更高层的概念问题，再基于这种“退一步”的理解扩展查询。

`HyDE`  
先让模型生成一段“假设性文档”，再用这段文档去检索。这适合概念型、解释型问题。

`complex`  
表示问题更复杂，需要同时结合多种扩展方式，所以它会同时使用 step-back 和 HyDE。

这个设计的关键点是：  
我不是固定写死一种改写，而是让系统根据问题类型动态路由。

---

### Q30：什么是 Step-back？为什么它有效？

**回答：**

Step-back 可以理解成“先退一步，再看问题”。

很多用户的问题太具体，甚至带着业务细节、文件名、日期、术语。如果只按原句检索，系统可能被这些细节限制住。

Step-back 的做法是先把问题抽象成更高层的问题。  
比如：

- 原问题：为什么我的缓存没有失效？
- Step-back：缓存失效机制通常依赖哪些条件？

这样做的意义是，系统不仅去找“这个具体词”，还去找它背后的通用原理。

它特别适合那些“表面在问细节，实际在问机制”的问题。

---

### Q31：什么是 HyDE？你为什么要用它？

**回答：**

HyDE 的全称可以理解为“假设性文档嵌入检索”。

它的思路是：  
如果用户的问题过于抽象，直接拿问题去检索可能不太像文档语言，那我就先让模型生成一段“可能包含答案的文档片段”，再用这段更像文档的话去检索。

这样做的好处是：

- 用户问题更像“查询”
- 知识库内容更像“说明文档”

HyDE 就是在两者之间搭一座桥。

它尤其适合：

- 定义类问题
- 原理类问题
- 概念解释类问题

---

### Q32：为什么要让模型决定用 step_back、hyde 还是 complex？

**回答：**

因为不同问题适合的检索增强方式不一样。

有些问题很具体，step-back 更有帮助。  
有些问题很抽象，HyDE 更有效。  
还有些问题既具体又复杂，需要两者结合。

如果我人为写很多 if-else 规则，维护成本会很高，而且很难覆盖所有表达方式。  
所以我用一个路由模型来做结构化判断，让它输出：

- `step_back`
- `hyde`
- `complex`

这样整个系统的适应性更强，也更接近真实用户场景。

---

## 八、项目创新点五：实时 trace 与可解释性

### Q33：你项目里的 trace 是怎么实现的？

**回答：**

我的 trace 分成两层。

第一层是“实时步骤 trace”，也就是系统正在做什么：

- 正在检索知识库
- 正在评估文档相关性
- 正在重写查询
- 正在做 HyDE
- 正在扩展检索

这部分是通过 `emit_rag_step()` 发事件，然后通过 `asyncio.Queue + SSE` 实时推送到前端。

第二层是“最终结构化 trace”，也就是一轮对话结束后，把整个 RAG 过程整理成一个对象，包括：

- 原查询
- 扩展查询
- 评分结果
- 检索模式
- 是否触发 rerank
- 是否 auto-merge
- 检索到的文档片段

最终这个 `rag_trace` 会跟消息一起保存到数据库中，后续查看历史会话时也能看到。

---

### Q34：你为什么要做 trace？它的价值是什么？

**回答：**

trace 的价值非常大，我觉得至少有四个方面。

第一，提升用户体验。  
用户不会看到一个空白页面等很久，而是知道系统正在做什么。

第二，提升可解释性。  
用户能看到系统检索了哪些片段、有没有重写查询、有没有做 rerank，这样更容易信任系统。

第三，方便调试。  
如果回答不好，我可以快速判断问题出在检索、评分、改写还是生成。

第四，方便后续优化。  
因为 trace 是结构化的，我以后甚至可以统计：

- 哪类问题经常触发 rewrite
- 哪类问题检索经常失败
- rerank 对结果提升有多大

所以 trace 不只是“好看”，它是一个真正有工程价值的观测能力。

---

### Q35：你的 trace 和大模型原始思维链有什么区别？

**回答：**

这个区别非常重要。

我的 trace 不是模型的原始 chain-of-thought，也不是把模型脑子里的所有推理都暴露出来。  
它是我自己设计的一套“业务级执行轨迹”。

它记录的是：

- 系统调用了哪个工具
- 检索做了什么
- 查询改写做了什么
- 检索返回了什么

也就是说，它展示的是“系统流程”，不是“模型内部隐式推理”。

这样做更安全，也更适合产品化，因为：

- 不会泄露不必要的模型思维细节
- 更稳定
- 更可控
- 对用户更有解释价值

---

### Q36：为什么你用 SSE 而不是 WebSocket 做流式 trace？

**回答：**

因为这个场景本质上是“服务端单向持续推送”，SSE 已经足够合适。

SSE 的好处是：

- 实现简单
- 和 HTTP 兼容性好
- 前端用 `fetch + reader` 就能接
- 对“服务端持续输出文本和事件”这种模式非常自然

WebSocket 更适合双向实时通信，比如协同编辑、多人对战、客户端频繁主动发消息。  
而我的场景主要是：

- 用户发一次请求
- 服务端持续往回推内容和 trace

所以 SSE 是更轻量、更合适的选择。

---

## 九、流式输出与并发设计

### Q37：流式回答是怎么实现的？

**回答：**

流式回答的核心是两部分。

第一部分是模型侧流式生成。  
我使用 Agent 的 `astream(stream_mode="messages")` 来拿到增量输出的 `AIMessageChunk`。

第二部分是后端把这些 chunk 包装成 SSE 事件，持续 `yield` 给前端。

前端再用 `ReadableStream` 逐段读取、逐段解析、逐段渲染，就形成了打字机式输出效果。

这套机制的好处是：

- 首字出现更快
- 用户等待感更低
- 可以和实时 trace 一起流式展示

这比等所有结果生成完再一次性返回，用户体验要好很多。

---

### Q38：为什么你的实时 trace 要走统一队列，而不是分开传？

**回答：**

因为回答正文和 trace 本质上都属于“同一次会话输出流”，统一队列更容易管理顺序和并发。

我这里把所有事件都放进一个 `asyncio.Queue`，包括：

- `content`
- `rag_step`
- `trace`
- `error`

这样做有几个好处：

- 流的出口统一
- 事件顺序更容易控制
- 前端协议更简单
- 后端不会为不同类型的事件开多套通道

简单理解，就是把所有“这次回答产生的输出”统一排队，然后按顺序推给前端。

---

### Q39：你为什么要用 `call_soon_threadsafe`？

**回答：**

因为 RAG 的步骤事件不一定总是在主异步线程里产生。

在流式对话中，Agent 工具调用和主响应流可能处于不同执行上下文。  
如果某个工具步骤直接去操作主事件循环里的异步队列，可能会有线程安全问题。

所以我先把当前事件循环保存下来，再通过 `call_soon_threadsafe` 把 `queue.put_nowait` 安全地投递回主 loop。

这个设计说明我考虑了异步和线程之间的边界，而不是只在“单线程理想情况”下写代码。

---

## 十、数据模型与会话管理

### Q40：为什么会话和消息要落 PostgreSQL，而不是只放 Redis？

**回答：**

因为 Redis 更适合缓存，不适合当长期真相源。

会话和消息属于核心业务数据，有这些特点：

- 要长期保存
- 要支持历史查看
- 要支持用户隔离
- 要支持删除和一致性维护

这些都更适合 PostgreSQL。

Redis 在这里扮演的是加速层，而不是最终存储层。  
也就是说：

- PostgreSQL 负责“存得住”
- Redis 负责“取得快”

这是一个很典型的缓存架构。

---

### Q41：为什么消息表里要存 `rag_trace`？

**回答：**

因为我希望每一条 AI 回复都不仅有“结果”，还有“这条结果是怎么来的”。

如果只把回答文本存下来，那后续查看历史时只能看到答案，看不到过程。  
但把 `rag_trace` 一起存下来后，历史会话就不只是聊天记录，而是完整的问答执行记录。

这对两个场景特别有价值：

- 用户回看：能看到当时系统检索了哪些内容
- 开发排查：能复现当时的系统行为

所以 `rag_trace` 存库，本质上是在做“可回放的 AI 会话记录”。

---

### Q42：为什么要给普通用户和管理员区分权限？

**回答：**

因为知识库管理和知识库使用是两种完全不同的权限。

普通用户应该能：

- 登录
- 对话
- 查看自己的历史记录

管理员才应该能：

- 上传文档
- 删除文档
- 管理知识库内容

如果不做角色隔离，会出现很明显的风险：

- 普通用户误删知识库
- 任意用户上传脏文档污染系统
- 无法控制数据来源

所以这不是一个“锦上添花”的功能，而是面向真实使用场景必须有的安全设计。

---

## 十一、缓存设计

### Q43：项目里 Redis 主要缓存了什么？

**回答：**

主要缓存了三类内容。

第一类，会话消息列表。  
用户进入某个会话时，不需要每次都查数据库。

第二类，会话摘要列表。  
比如左侧历史会话列表，属于高频读取。

第三类，父块文档内容。  
Auto-merging 时经常要按 `chunk_id` 取父块，如果完全走数据库会增加延迟，所以我也做了缓存。

也就是说，Redis 不是“随便加一个缓存”，而是专门围绕两个高频热点设计的：

- 聊天历史
- 父块回取

---

### Q44：缓存一致性是怎么保证的？

**回答：**

我没有做特别复杂的分布式一致性方案，而是采用了比较实用的“写后失效”策略。

比如：

- 保存消息后，会刷新消息缓存并删除会话列表缓存
- 删除会话后，会删除该会话缓存和会话列表缓存
- 更新父块时，会同步更新对应缓存
- 删除父块时，会删除对应缓存

这种方式的优点是简单、稳定、足够适合当前项目规模。  
在中小型项目里，这种缓存失效策略通常是性价比很高的做法。

---

## 十二、工程难点与取舍

### Q45：这个项目你觉得技术上最难的点是什么？

**回答：**

我觉得最难的不是某个单独模块，而是“把多个复杂模块稳定串起来”。

如果细分，我会说最难的有三个。

第一，RAG 不是一次检索，而是多阶段链路。  
要考虑检索、评分、改写、扩展检索、重排、合并等多个环节之间的状态流转。

第二，流式输出和 trace 并发。  
回答正文和检索步骤需要同时实时展示，这里面涉及异步队列、事件顺序、线程安全。

第三，数据一致性。  
文档上传和删除时，要同时维护：

- Milvus 数据
- BM25 状态
- 父块存储
- Redis 缓存

这些都不能只顾一头，否则系统长期运行后会出现状态漂移。

---

### Q46：如果面试官说你这个项目“功能多，但不够聚焦”，你怎么回答？

**回答：**

我会承认它是一个“完整链路型项目”，而不是单点算法项目，但这恰恰是它的价值。

它的重点不是单独证明某个算法，而是证明我能把一个 AI 应用从“能力想法”落到“可运行系统”。

这个项目的聚焦点其实很明确，就是：

> 围绕知识库问答，做一套可靠、可解释、可扩展的 AI 助手系统。

所有功能都围绕这个目标服务：

- 登录权限是为了安全使用
- 文档上传是为了知识接入
- 混合检索是为了提升召回
- 查询改写是为了提升复杂问题效果
- trace 是为了可解释性
- 流式输出是为了用户体验

所以它不是“功能堆砌”，而是围绕同一个业务目标展开的完整设计。

---

### Q47：这个项目有哪些地方你觉得还能继续优化？

**回答：**

我觉得至少还有六个方向。

第一，评估体系更完善。  
现在已经有基础测试和评估脚本，但还可以补充更系统的 RAG Benchmark 和人工标注集。

第二，前端工程化升级。  
可以迁移到 `Vite + Vue` 或更现代的前端架构。

第三，文档解析能力增强。  
比如表格、图片、复杂版式、扫描件 OCR。

第四，检索策略继续优化。  
比如更精细的 rerank 参数调优，或者引入查询分类。

第五，监控和日志。  
比如更系统的 tracing、延迟指标、召回命中率分析。

第六，多工具和多 Agent 扩展。  
未来可以增加数据库助手、网页搜索、任务规划等工具。

所以我认为这个项目已经是一个不错的原型，但还有很大的演化空间。

---

### Q48：如果文档量变得很大，你觉得现在的方案会遇到什么瓶颈？

**回答：**

主要可能遇到四类瓶颈。

第一，文档解析和入库耗时。  
大量文档上传时，embedding 和写库会变慢。

第二，BM25 状态维护成本。  
本地 JSON 持久化在更大规模下可能不够优雅。

第三，检索排序成本。  
候选集变大后，rerank 和 auto-merging 的成本会上升。

第四，前端可视化复杂度。  
如果 trace 和文档片段太多，前端展示也会变重。

如果进入更大规模场景，我会考虑：

- 异步任务队列化
- 更专业的搜索引擎配合
- 更强的索引管理方案
- 更完整的观测与限流机制

也就是说，我当前方案是面向中小规模知识库很合适，但我也清楚它未来的扩展边界。

---

## 十三、项目里的“为什么不是别的方案”

### Q49：为什么不直接把所有历史对话都送给模型，而要做摘要？

**回答：**

因为上下文窗口和成本都有限。

如果把所有历史消息一直累积下去，会带来三个问题：

- token 成本越来越高
- 延迟越来越大
- 模型容易被冗余上下文干扰

所以我在消息很多时，会先把旧消息做摘要，再把摘要作为系统消息放进去，只保留后面的新消息。

这其实是一个很典型的“记忆压缩”思路：  
保留长期重要信息，减少上下文负担。

---

### Q50：为什么要保留同步接口 `/chat` 和流式接口 `/chat/stream` 两套？

**回答：**

因为两种接口适合不同场景。

`/chat` 更适合：

- 脚本测试
- 简单集成
- 不需要流式体验的调用方

`/chat/stream` 更适合：

- Web 聊天界面
- 希望降低等待感的场景
- 需要实时展示 trace 的交互场景

保留两套不是重复，而是兼顾易用性和用户体验。

---

### Q51：为什么你要把 trace 做成结构化对象，而不是一段日志文本？

**回答：**

因为日志文本不利于后续展示、存储和分析。

如果只是一段文本，比如：

> 开始检索 -> 检索完成 -> 评分为 no -> 开始改写 -> 再检索

那前端可以显示，但很难做更细的处理。

而结构化对象的好处是：

- 前端可以按字段展示
- 数据库可以直接存 JSON
- 后续可以做统计分析
- 不同模块可以持续往里面补字段

所以结构化 trace 更像“业务数据”，而不是“开发日志”。
