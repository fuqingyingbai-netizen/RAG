# 多轮问题判断与回答显示验收（2026-11-11）

本次只更新 main，不部署；Ragas 与知识库事实质量评测由另一会话继续。

## 如何判断

系统判断的是本轮检索问题是否需要补全上下文，而不是简单按“第几次提问”分类。

- 完整新问题直接检索；已明确要求整理所选资料、没有历史指代的任务也直接检索。
- 历史指代、格式转换、省略式问法进入模型补全。补上了“客户数呢”“那某公司呢”“之前的答案”“同样比较”“有哪些风险”“怎么收费”等遗漏入口。
- 补全显式提供最近用户问题。本轮明确对象优先，省略对象才继承最近明确对象；多个并列对象仍不清楚时请求澄清。不能因为不了解公司或指标值，就认为检索对象不明确。
- 历史仅用于理解任务，引用编号会清理；最终事实仍重新检索。原有权限、会话隔离与并发占用检查保留。

这仍是规则与模型配合的方式，并非所有自然语言都能无误识别。某些完整问题也可能多走一次补全，不能把样本通过率当成通用识别准确率。

## 实际测试

- 新增 26 种表达的路由检查，并重复 20 次双轮话题切换。修改前，针对性集合中的 10 种表达遗漏了补全，重复切换测试也失败；修改后新增路由测试全部通过。
- 会话与路由回归 57 项通过；补充最近用户问题字段后，相关接口与路由专项 37 项通过。前端与请求生命周期检查 63 项通过。
- 真实模型使用虚构公司、两组八轮历史，只检查问题补全，不生成业务答案。第一轮并发探测 8/16 符合预期；随后串行探测 14/16 符合预期：一次确认 HTTP 429 限流，一次错误地请求澄清。失败记录保留，见验收 JSON。
- 串行探测中，需要模型且返回 HTTP 200 的补全耗时约 7–85 秒；完整问题在这些样本中不额外调用模型。因此当前不能宣称频繁交互稳定秒回。后续提示词收紧后的定点复核另存，不能冒充完整重跑。
- 最终提示词的两项定点检查：最近对象“丙公司怎么收费”正确补全；切换“乙公司”的请求被限流阻断，尚未复核通过。更早的明确切换样本曾成功，因此不能把该场景既往失败或既往成功当作最终版本的全面结论。

程序检查的是对象、任务关键词、模型调用次数及应澄清时的空值；这不是 Ragas 分数，也不是业务答案准确率或容量压测。

## 显示修复

复用现有 Marked 与 DOMPurify 渲染标题、列表、加粗和表格；引用改成来源编号按钮，点击定位到当前回答的对应片段，原始回答及导出引用不改写。旧回答也可使用新显示方式，无需重新生成。

未知引用明确标为未核验；代码示例保持原样；原文 HTML、脚本、危险链接和外部图片不会直接执行或加载。解析器不可用时安全退回转义文本。相同回答缓存已净化的排版，减少计时器刷新时的重复解析。

浏览器验收覆盖桌面、390px、触屏引用按钮、暗色、流式更新、鼠标与键盘打开准确片段；无页面脚本错误及外部图片请求。脚本：`scripts/check-knowledge-answer-ui.py`。
